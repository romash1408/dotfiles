# Таблица и синк money-sync: как это устроено

Справка для агента без доступа к репозиторию money. Прочитайте её до первой записи в таблицу.
Всё, чего здесь нет, не додумывайте. На крайний случай есть публичный код сервиса:
https://gitlab.com/romash1408/zenmoney2sheets (README, `internal/sheetmodel`, `internal/syncer`).
Если и там ответа нет, остановитесь и спросите пользователя.

## Система

- **ZenMoney** — основное хранилище операций. Банки туда сами не подтягиваются, поэтому
  операции О!Банка пользователь вносит через таблицу.
- **Google-таблица** — интерфейс для просмотра, правки и создания операций.
- **Сервис money-sync** (Go, docker) живёт на домашнем сервере и доступен по `http://hp.wg:8090`.
  `POST /sync` синхронизирует таблицу и ZenMoney в обе стороны, конфликты разрешает ZenMoney.
  Если задан `SYNC_SECRET`, его передают в заголовке `X-Sync-Secret`.
  - `POST /sync?dryRun` показывает, что изменилось бы, и ничего не пишет (ни в ZM, ни в таблицу).
  - `GET /healthz` проверяет, что сервис жив.
  - Одновременно идёт только одна синхронизация, параллельный запрос получает 409.
  - Ответ — JSON со счётчиками (`sentNew`, `sentEdited`, `receivedTransactions`, `rowsWritten`).
- **Состояние живёт только в таблице.** У сервиса нет своей базы.

Агент запускает синк **один раз — перед стартом** (`money.py sync`), чтобы таблица была свежей.
После вставки синк не запускайте: пользователь сначала проставит категории, а синхронизирует сам.

## Лист «Операции»

- **Строка 1 — служебная.**
  - `B1` — lastServerTimestamp. Не трогать: очистка B1 запускает полный ресинк.
  - `D1` — статус последнего синка: `OK …` или `ERROR …`.
  - `Q1` — id пользователя ZM.
- **Строка 2** — заголовки. **Данные** начинаются со строки 3.
- **Сортировка:** дата по убыванию, внутри дня — «Создана» по убыванию (свежие сверху).

| Кол. | Заголовок | Смысл |
| --- | --- | --- |
| A | id | UUID операции. **Пусто — новая строка**, синк создаст операцию и впишет id |
| B | Дата | серийная дата Sheets (число, эпоха 1899-12-30); текстом принимается `YYYY-MM-DD` |
| C | Категория | имя из колонки «Для операций» листа «Категории»; у переводов — плейсхолдер `Перевод` |
| D | Описание | комментарий (comment) |
| E | Получатель | имя из «Для операций» листа «Получатели». Произвольный текст уйдёт в сырой `payee` без контрагента |
| F | Теги | остальные категории через запятую |
| G | Счёт | имя из «Для операций» листа «Счета», для нас `O!Bank R *3720` |
| H | Валюта | валюта, в которой операция реально прошла; обычно совпадает с валютой счёта (KGS) |
| I | Сумма | >0 приход, <0 расход, в валюте операции (H) |
| J | Чек | qrCode |
| K | Новая | `TRUE` — пользователь ещё не просмотрел операцию. Синк сохраняет флаг и у строк, созданных из таблицы |
| L | Удалена | `TRUE` удаляет операцию в ZM. Такие строки остаются на листе (это удалённые дубли), сверка их не учитывает |
| M | Сумма в валюте счёта | на сколько изменился баланс счёта; синк заполняет её сам, у новой строки можно оставить пусто |
| N, O | Создана, Изменена | служебные времена (UTC); не редактировать |
| P | Контрольная сумма | считает синк. Несовпадение означает, что строку отредактировали, и правка уйдёт в ZM |
| Q | raw | полный JSON операции из ZM (`created`, `originalPayee`, `op*`…); не редактировать |
| R | — | **личная пометка пользователя**, синк её не читает. Агент пишет сюда `suggested` |

Валюты: если H совпадает с валютой счёта, то I = M, и M — производная. При конвертации
(например, покупка в USD с сомового счёта: H=USD, I=−11.98, M=−1048.25) в ZM как сумма по счёту
уходит M, а знак берётся из I. Поэтому при конвертации правят M (`fix-amount --account-sum`).

### Что синк делает со строками

- **Пустой id** → новая операция в ZM. Её «Создана» синк вычисляет **по месту строки в листе**:
  между временем соседей того же дня. Поэтому `insert` ставит строку в нужное место дня.
- **Изменена любая колонка** (контрольная сумма не совпала) → правка уходит в ZM. Именно поэтому
  существующие строки трогать нельзя, кроме явного `fix-amount`.
- **Перевод** занимает две строки (списание и зачисление) с общим id. Новый перевод — две строки
  с одинаковым не-UUID маркером в id (например, `t1`). Агент переводы не создаёт: «+X перевод
  между своими счетами» уже есть в таблице с другой стороны, либо выносится в отчёт.
- **Невалидная строка** прерывает синк целиком: ничего не отправляется, в D1 пишется `ERROR …`.
  Невалидная — это неизвестный счёт, категория или валюта, кривая дата или сумма, непарный маркер.
  Поэтому категорию не пишите, если её нет в «Категории», а счёт пишите точно `O!Bank R *3720`.
- **Физически удалённая строка** в ZM не удаляется и вернётся. Агент строки не удаляет вообще.

### Справочные листы

«Счета», «Категории», «Получатели», «Валюты» заполняются только из ZM. Колонка «Для операций» —
уникальное имя для ссылок с листа операций. Тёзки уточняются: `Досуг / Музыка`, `Наличка (ccard)`.

## Что пишет `money.py insert`

Вставка — одна атомарная `batchUpdate`: `insertDimension` плюс значения. Существующие строки только
сдвигаются вниз и не меняются. Новая строка заполняется так:
- id пусто;
- Дата, Описание, Получатель (если однозначен), Счёт, Валюта, Сумма;
- «Новая» = TRUE, «Удалена» = FALSE;
- R = `suggested`.

Остальное (M, N, O, P, Q) заполнит синк. Место строки — внутри своего дня перед первой строкой,
у которой `created` в raw меньше времени операции банка (Бишкек UTC+6 → UTC).

## Если что-то пошло не так

- `money.py sync` вернул ошибку или D1 ≠ `OK` → стоп, сообщить текст пользователю. Не чинить
  таблицу самостоятельно.
- `hp.wg` не резолвится или недоступен (нет WireGuard) → стоп, сказать пользователю.
- Ошиблись при вставке → не удалять строки, а сообщить номера пользователю. Строки без id
  ещё не ушли в ZM, пользователь удалит их сам.
